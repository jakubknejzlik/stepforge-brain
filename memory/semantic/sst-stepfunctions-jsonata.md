# SST v3 StepFunctions — JSONata data flow gotchas

## Context
Discovered during the Tier1-4 SST StepFunctions test campaign (2026-08-10/11, 32 scenarios) validating the `sst.aws.StepFunctions` component before using it for real workflow builds.

- [MEM-3] SST v3's `sst.aws.StepFunctions` component is JSONata-only — every state serializes with `QueryLanguage:'JSONata'` (see `.sst/platform/src/components/aws/step-functions/state.ts` `toJSON()`). There is NO `InputPath`/`OutputPath`/`ResultPath`/`Parameters` (legacy JSONPath-era ASL fields) exposed anywhere in the fluent API (checked state.ts, pass.ts, task.ts, map.ts, parallel.ts, choice.ts, wait.ts, fail.ts, succeed.ts). JSONata equivalents: `output` (reshapes/selects data flowing to next state, ~InputPath+OutputPath combined) and `assign` (stores workflow variables accessible via `$varName` in later states, ~ResultPath analogue). Confirmed via Tier1 #7 InputOutputFiltering: `assign:{originalInput:'{% $states.input %}'}` in one Pass state was readable as `$originalInput.meta` two states later even after `output` narrowed the payload.
- [MEM-5] Chained `lambdaInvoke`s bug: default output is the raw SDK response wrapper (`.Payload` nesting — the default `lambdaInvoke` output is the full raw SDK invoke response, not narrowed to `Payload`), so feeding step1's default output straight into step2's payload as `$states.input` silently produces wrong values (undefined arithmetic → NaN → JSON null) instead of an error. Caught via Tier2 #13: `doubled:null` instead of 22, fixed by adding `output:'{% $states.result.Payload %}'` on step1. **Lesson: ALWAYS narrow a `lambdaInvoke`'s output to `.Payload` (or specific fields) before chaining into the next state's payload** — the unnarrowed wrapper is a silent-failure trap, not a hard error.
- [MEM-6] `lambdaInvoke` Task payload as a bare JSONata scalar expression fails at RUNTIME (not deploy time) with `States.Runtime` / "The value for the field Payload must be a STRING" — AWS's `lambda:invoke` integration requires the resolved Payload to be an object (serialized to JSON), not a bare number/string. Caught via Tier2 #14 Map: processor `payload:'{% $states.input %}'` over `items:[1..6]` (each item a plain number) failed every iteration. Fix: always wrap scalar payloads in an object, e.g. `payload:{value:'{% $states.input %}'}`. **This class of bug is invisible at `sst deploy` time — only surfaces when you actually run an execution**, reinforcing why every new scenario needs a real start-execution check, not just a successful deploy.

Related: the same raw-SDK-wrapper shape (not narrowed to a clean payload) also applies to `sqsSendMessage` and `snsPublish` task outputs (Tier3 #19/#20) — same pattern as MEM-5, narrow before chaining.
