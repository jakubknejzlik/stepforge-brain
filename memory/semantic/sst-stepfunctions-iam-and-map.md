# SST v3 StepFunctions — IAM baseline & Map fault-tolerance

## Context
Discovered during the Tier1-4 SST StepFunctions test campaign (2026-08-10/11, 32 scenarios) validating the `sst.aws.StepFunctions` component before using it for real workflow builds.

- [MEM-8] SST v3 `sst.aws.StepFunctions` attaches a FIXED baseline IAM policy to every generated role regardless of what the state machine actually does — `events:*` on `Resource:*` (full EventBridge wildcard) + `states:StartExecution`/`states:DescribeExecution` on `Resource:*` — confirmed present even on a trivial Wait→Pass→Succeed dummy with zero Task integrations. Only app-specific permissions added via explicit `.permissions()`/integration helpers (dynamodb:PutItem/GetItem, sqs:SendMessage, etc.) are correctly least-privilege scoped to specific resource ARNs — SST DOES support scoping when asked, but the unconditional baseline is broad. Not necessarily a bug (`events:*` likely backs X-Ray/observability signaling, `states:*` backs `.sync` nested-execution support) but **worth flagging for IAM audits**: least-privilege reviews of SST-generated SFN roles should expect this baseline and not assume it's an app-specific over-grant. Verified via IAM audit (Tier4 #29) across 4 different roles — baseline consistent, no managed/attached policies anywhere, all inline.
- [MEM-10] `ToleratedFailurePercentage`/`ToleratedFailureCount` on a Map state is SILENTLY IGNORED by AWS Step Functions in INLINE mode — confirmed empirically: injected the field via the `transform.stateMachine` callback pattern (mutating raw pulumi state-machine args before creation), verified it WAS present in the deployed ASL, ran 4 items with 1 intentional failure (25%, under the 50% tolerance) — execution still FAILED outright. **Fix: Map must use `mode:'standard'` (DISTRIBUTED processing)** for the tolerance to take effect; re-run with identical input SUCCEEDED with the failed item captured inline as `{Status:FAILED,Error,Cause}` instead of aborting. This is an AWS platform restriction (fault-tolerance is a distributed-mode-only Map feature), not an SST gap — but SST's Map component gives no hint/validation that the field is a no-op in inline mode (and doesn't expose the field at all — see MEM-9 transform workaround).
