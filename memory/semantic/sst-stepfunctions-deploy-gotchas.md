# SST v3 StepFunctions — deploy/build gotchas

## Context
Discovered during the Tier1-4 SST StepFunctions test campaign (2026-08-10/11, 32 scenarios) validating the `sst.aws.StepFunctions` component before using it for real workflow builds.

- [MEM-4] SST v3 JSONata-mode StepFunctions component — ANY explicit Task-level `timeout` arg (any integration: response/token) fails deploy with AWS provider error `ERROR (SCHEMA_VALIDATION_FAILED): Field Timeout is not supported: provider=aws@7.20.0`. **Root cause corrected — see [MEM-11]:** this is a one-line SST bug (`task.ts` serializes the field as literal key `Timeout`; per AWS docs the correct ASL field name is `TimeoutSeconds` in both JSONPath and JSONata modes — `Timeout` was never valid), not a genuine AWS/JSONata provider gap as originally assumed. **Workaround: Parallel-race pattern** (Wait N sec → Fail state, racing the slow/non-callback branch) instead of the built-in timeout field — still required until the upstream fix lands. Used for Tier2 #12 (task timeout) and #18a (waitForTaskToken timeout) — the native timeout field is unusable for both integration types.
- [MEM-11] Correction to MEM-4's root cause, verified empirically: patched `.sst/platform/src/components/aws/step-functions/task.ts:327` locally (`Timeout`→`TimeoutSeconds`), deployed a minimal repro (lambdaInvoke + sleepy handler, 3s SFN timeout vs 6s lambda sleep) — deploy succeeded (no SCHEMA_VALIDATION_FAILED), `describe-state-machine` confirmed `TimeoutSeconds` present in the deployed ASL, and a real execution correctly failed with `States.Timeout` at runtime. Fix verified end-to-end, not just schema-valid; reverted local patch after testing. Upstream fix submitted: **anomalyco/sst#6966** (fork jakubknejzlik/sst, branch `fix/step-functions-task-timeout-field-name`, base `dev`) — not yet merged as of 2026-08-11.
- [MEM-12] Tracking anomalyco/sst#6966 (the MEM-4/MEM-11 `Timeout`→`TimeoutSeconds` fix) for merge/release. Once it lands, the Parallel-race workaround above is no longer needed for Task-level timeout — check PR status before reaching for the workaround on new SST workflow work, and update this entry once merged.
- [MEM-7] SST v3 Resource linking (`import {Resource} from 'sst'` in a lambda handler) requires the `sst` npm package itself as a runtime dependency in `package.json` — it's NOT auto-provided just because `sst-env.d.ts` declares the module, and NOT the same as the `sst` CLI (resolved separately, e.g. from npx cache). Deploy fails at build time with esbuild error `Could not resolve "sst"` pointing at the handler file. **Fix: `bun add sst@<version matching CLI>`** (e.g. 4.17.1). First hit in Tier3 #24 (S3 Bucket linked function) — Tier1/Tier2 handlers never needed Resource linking so this never surfaced before.
- [MEM-9] SST v3 `sst.aws.StepFunctions` exposes NO tracing/X-Ray argument anywhere in the fluent `StepFunctionsArgs` API (checked `step-functions.ts` `createStateMachine`) — `tracingConfiguration` defaults to `{enabled:false}` for every generated state machine, confirmed even on a trivial dummy. **Workaround:** `transform.stateMachine` as a FUNCTION (not object merge) — SST's `transform()` helper (`component.ts`) supports transform being a callback `(args,opts,name)=>void` that mutates the raw pulumi `aws.sfn.StateMachineArgs` in place before resource creation, e.g. `transform:{stateMachine:(args)=>{args.tracingConfiguration={enabled:true}}}`. Same mechanism (`args.definition` is a pulumi `Output<string>` from `$jsonStringify`, supports `.apply(json=>...)`) can inject ANY ASL field SST's per-state builders don't expose — there's no raw-ASL-state escape hatch at the individual-state level, only this whole-definition one. CloudWatch `AWS/States` metrics (ExecutionsSucceeded/Failed/Started/Aborted/TimedOut, ExecutionTime, etc.) are emitted automatically by AWS regardless of SST config — no setup needed, unlike tracing.
