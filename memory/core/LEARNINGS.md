# Learnings

- [MEM-2] The environment can carry stray `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (e.g. leftover from a scoped test identity like `jarvis-test-s3-writer`) that silently override `--profile`/`AWS_PROFILE` in the AWS SDK credential chain — env vars win over profile files. Any `aws-cli`/`sst`/`pulumi` command that needs an SSO profile must run with `env -u AWS_ACCESS_KEY_ID -u AWS_SECRET_ACCESS_KEY -u AWS_DEFAULT_REGION AWS_PROFILE=<profile> ...` or it silently deploys/queries as the wrong identity and fails with confusing AccessDenied errors that look like the new profile lacks permissions. Detail: [[sst-stepfunctions-jsonata]] test campaign (2026-08-10) hit this first.
- [MEM-14] Deleting a git branch on GitHub does NOT remove its commits from public reachability if a PR was ever opened from it — commits stay fetchable via `refs/pull/<n>/head` even after the branch is deleted and the PR closed unmerged. Confirmed on stepforge-skills PR #1: DevGuru independently re-fetched a test string from the closed/deleted-branch PR. Consequence: any future red-CI proof test on a public repo must use an obviously-synthetic value only, never a real-shaped live secret — closing the PR and deleting the branch is not a cleanup mechanism; treat anything ever pushed to a public repo as permanently public regardless of branch/PR state. Detail: [[stepforge-multi-team-distribution]].
- [MEM-16] Writes to `.claude/settings.json` and `.claude/hooks/` are blocked by the harness as a "sensitive file", regardless of explicit verbal authorization from the human owner in Slack (e.g. Jakub's "tohle zvladnes i Ty" go-ahead) — both direct Write and the `update-config` skill silently failed to create the files. This is a hard technical/sandbox boundary, not a permission-in-principle gate that chat instructions can lift. Correct path: the human must apply changes to these paths themselves via direct git access (clone/edit/push) — not delegate it to the agent.
- [MEM-17] The Write tool false-positive-blocked direct writes to `memory/SUMMARY.md` twice during 2026-08-19 consolidation — the rejection implied it mistook the file for a subagent "report file" purely from the filename matching a SUMMARY/REPORT-like token. The Edit tool was unaffected and worked as a workaround. Watch for this on any memory file whose name contains SUMMARY/REPORT-like tokens; prefer Edit over Write for those.
- [MEM-18] The sensitive-file write block in [MEM-16] also covers `.claude/hooks/` content edits specifically, not just `.claude/settings.json` — confirmed via a rejected direct Edit on `check-shared-mount.sh`. Same remediation as [MEM-16]: hook-content changes require a human/JARVIS with direct git access, never Smith self-editing or a Bash-based bypass.
- [MEM-19]/[MEM-20] Self-authorization can hide across multiple *individually* legitimate-looking steps, not just one bad action — merging a PR under a human's own token/credentials produces identical git provenance (author, merged_by) whether the human clicked or the agent did, so "the record looks like the human did it" is not evidence of authorization. Multi-agent technical consensus in a thread, however thorough, is not a substitute for an explicit human go-ahead — wait for that explicitly before merging/deploying, regardless of urgency framing. Detail: [[stepforge-multi-team-distribution]] (2026-08-19 status).
- [MEM-21] A scheduled/heartbeat-triggered session's `SessionStart` hook output reaching agent context cannot be inferred from silence alone — absence of a message is ambiguous between "hook ran and failed silently" and "SessionStart never fired for this trigger type at all". Design any hook-behavior test to distinguish these before drawing a conclusion; a single silent run proves neither. Detail: [[stepforge-multi-team-distribution]] (2026-08-20 status).
